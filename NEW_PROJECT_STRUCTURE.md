# Project Structure

This is the smallest useful structure for the study. It keeps the research
concepts separate without creating a directory or file for every controller,
metric, or command.

The project has one plant, one uncertain parameter, three controller variants,
and one RL algorithm. The code structure should reflect that scope.

## Recommended tree

```text
lyapunov-shielded-residual-rl/
├── README.md
├── PROJECT_STRUCTURE.md
├── pyproject.toml
├── uv.lock
├── .gitignore
├── configs/
│   └── experiment.yaml
├── src/
│   └── cartpole_rl/
│       ├── __init__.py
│       ├── config.py
│       ├── plant.py
│       ├── controllers.py
│       ├── shield.py
│       ├── environment.py
│       ├── learning.py
│       ├── evaluation.py
│       ├── plotting.py
│       └── cli.py
├── tests/
│   ├── test_plant.py
│   ├── test_controllers.py
│   ├── test_shield.py
│   ├── test_learning.py
│   └── test_pipeline.py
├── paper/
│   └── main.tex
└── runs/                       # Generated and ignored by Git
```

Use `uv.lock` if the project uses `uv`. If another environment manager is
chosen, replace it with that tool's single lock file; do not maintain both
`pyproject.toml` and a hand-written `requirements.txt`.

## Module responsibilities

| Path | Owns |
| --- | --- |
| `README.md` | Plain-language research question, scope, non-claims, setup, and the exact commands needed to reproduce the study. |
| `configs/experiment.yaml` | Every experiment choice: seeds, masses, controller parameters, SAC settings, evaluation grids, horizons, and output options. |
| `config.py` | Loading, validating, and freezing the configuration. No experiment constants should be scattered through the code. |
| `plant.py` | State and input conventions, cart-pole dynamics, integration, equilibrium definition, physical limits, and nominal versus true pole mass. |
| `controllers.py` | A small common controller interface, the energy-shaping/LQR nominal controller, the bounded residual wrapper, and construction of the three evaluated variants. |
| `shield.py` | The Lyapunov-based residual filter, solver status, activation status, infeasibility handling, and shield diagnostics. |
| `environment.py` | The RL observation, reward, termination rules, action normalization, and pole-mass randomization used during training. It must call `plant.py` rather than reimplement dynamics. |
| `learning.py` | SAC creation, training, checkpoint saving/loading, and seed handling. Keep SAC-specific code here. |
| `evaluation.py` | Deterministic rollouts on the frozen mass grid and all reported measurements: success, fixed-point displacement, Jacobian spectral radius, basin samples, effort, track violations, Lyapunov-decrease violations, and shield statistics. |
| `plotting.py` | Figures and summary tables produced only from saved evaluation data. It must not train policies or run simulations. |
| `cli.py` | One command-line interface with `train`, `evaluate`, `plot`, and `smoke-test` commands. |
| `tests/` | Mathematical and pipeline contracts, not a second implementation of the study. |
| `paper/` | Report source. It consumes saved tables and figures; it does not contain analysis code. |
| `runs/` | Checkpoints, resolved configurations, raw evaluation tables, metadata, and figures generated by commands. |

## Controller composition

Do not implement three independent controller stacks. Build the experimental
controllers by composing the same nominal controller, residual policy, and
shield:

| Evaluated controller | Control law |
| --- | --- |
| Nominal | `clip(u_nominal(x))` |
| Residual SAC | `clip(u_nominal(x) + bounded_residual(x))` |
| Shielded residual SAC | `clip(u_nominal(x) + shield(x, bounded_residual(x)))` |

Every controller should expose the same operation:

```python
action, diagnostics = controller.act(state, deterministic=True)
```

`diagnostics` should contain only applicable fields, such as nominal action,
proposed residual, applied residual, shield activation, shield infeasibility,
and constraint margin. This avoids special-case logging in the evaluator.

## Configuration

Start with one canonical configuration:

```yaml
seeds: [0, 1, 2]

plant:
  nominal_pole_mass: ...

controller:
  action_limit: ...
  residual_limit: ...
  energy_shaping: ...
  lqr: ...

shield:
  enabled: true
  lyapunov_region: ...
  decrease_margin: ...
  infeasible_fallback: ...

training:
  algorithm: sac
  total_steps: ...
  mass_randomization: true
  pole_mass_range: [...]

evaluation:
  deterministic_policy: true
  pole_mass_grid: [...]
  horizon: ...
  initial_condition_grid: ...
  success_definition: ...
```

The displayed keys are a contract, not a complete parameter list. On every
run, validate the config and save the fully resolved version beside the
results.

## Generated run layout

Each training/evaluation run should be self-describing:

```text
runs/<run-name>/
├── resolved_config.yaml
├── metadata.json
├── checkpoints/
│   ├── seed_0/
│   ├── seed_1/
│   └── seed_2/
├── tables/
│   ├── episodes.csv
│   ├── local_stability.csv
│   └── basin.csv
└── figures/
```

- `metadata.json` records the timestamp, code revision, dependency versions,
  and command used.
- `episodes.csv` has one row per rollout and preserves per-seed values before
  aggregation.
- `local_stability.csv` stores the computed fixed point, displacement, and
  closed-loop Jacobian spectral radius for each controller, mass, and seed.
- `basin.csv` stores the sampled initial condition and its outcome. The basin is
  therefore an empirical sampled basin, not a formal region of attraction.
- Large step-by-step trajectories should be saved only when a figure or
  diagnostic needs them.

## Execution flow

```text
experiment.yaml
    → train SAC with randomized training masses
    → freeze one checkpoint per seed
    → evaluate all controllers deterministically on the wider frozen mass grid
    → save unaggregated tables
    → generate figures and report summaries from those tables
```

The evaluator must never retrain a policy, change the evaluation mass grid, or
sample a new grid implicitly.

Suggested commands:

```bash
uv sync
uv run cartpole train --config configs/experiment.yaml
uv run cartpole evaluate --config configs/experiment.yaml --run <run-name>
uv run cartpole plot --run <run-name>
uv run pytest
```

## Tests that matter

- `test_plant.py`: equilibrium, state conventions, integration consistency,
  physical parameter validation, and nominal/true mass separation.
- `test_controllers.py`: action bounds, residual bounds, LQR behavior near the
  upright equilibrium, and correct controller composition.
- `test_shield.py`: feasible filtering, inactive pass-through, constraint
  margin calculation, activation logging, and explicit infeasible fallback.
- `test_learning.py`: environment API, mass randomization range, deterministic
  reset by seed, and a short SAC smoke run.
- `test_pipeline.py`: a tiny train/evaluate/plot run that verifies output
  schemas and repeatability.

## Rules that keep the project minimal

1. Define the dynamics once in `plant.py`; training and evaluation use the same
   implementation.
2. Keep one YAML file until there is a real need for a second experiment.
3. Keep one CLI instead of separate scripts that duplicate setup and argument
   handling.
4. Save raw per-seed and per-rollout measurements before computing means or
   making figures.
5. Keep notebooks optional and disposable. No required logic should live in a
   notebook.
6. Do not create one file per controller or one file per metric while the
   implementations remain small.
7. Split `evaluation.py` into an `evaluation/` package only if it becomes hard
   to navigate. Natural later splits are `rollouts.py`, `stability.py`, and
   `basin.py`.
8. Describe the shield precisely: report its implemented condition,
   assumptions, activations, and failures. Do not turn empirical results into
   a claim of global or unconditional safety.

This layout is intentionally small. Modularity comes from clear ownership and
interfaces, not from maximizing the number of folders.
